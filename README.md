# Evidence Integrity Kit

A small, offline Python CLI for generating and verifying SHA-256 manifests for explicitly selected evidence files. Intended for reproducible security assessments, software test artifacts and research records. Unsigned operations use the Python standard library. Optional signed operations require PyCA cryptography and its dependencies. Runtime operations make no network calls.

## Requirements

Unsigned mode requires Python 3.11 or later on supported Windows and POSIX systems; native CI verifies CPython 3.11 and 3.13. The optional signing lock covers only CPython 3.11 and 3.13 on Linux x86-64 (glibc >= 2.34), Windows x86-64, and macOS ARM64. Other interpreter versions or architectures are not covered by the current hash allowlist. Signing provider release acceptance remains blocked.

The manifest and create preflight also limit the selection to 10,000 entries, 32,768 total path components, and 262,144 total Unicode path characters (at most 128 components per path). These limits bound trie construction, not total bytes of evidence, KDF work or wall-clock I/O. Do not expose the CLI as an untrusted-input service without separately enforced resource isolation.

Windows additionally samples native FILE_BASIC_INFO ChangeTime before hashing and at batch revalidation. This detects some changes hidden by a restored modification time; it is not an immutable snapshot or continuous writer exclusion.

## Explicit evidence protection selection

Breaking CLI safety change in this development candidate: create, verify and verify-signed require exactly one protection option. Choose the applicable native provider or `--assume-stable-tree` only when external writer and namespace isolation is trusted. Omission and conflicting modes must not implicitly select sampled verification. The stable-tree assertion is not a capability check; successful verification reports `protection.mode=assumed-stable-tree` and `isolation_verified=false`. Native mode failure never downgrades. The manifest/signature wire formats are unchanged; the Python library's legacy default remains sampled for compatibility and is not isolation proof. Sign operates on retained manifest bytes only and does not select evidence protection.

## Example

```sh
python evidence_integrity.py create --assume-stable-tree --root ./evidence scan.json notes.txt > manifest.json
python evidence_integrity.py verify --assume-stable-tree --root ./evidence --manifest manifest.json
```

Run `create` on a trusted, stable evidence directory. Keep the resulting manifest in a separate trusted location. The command prints JSON and does not write into the evidence directory. `verify` checks the listed files and produces a JSON report. Exit codes: `0` success, `1` mismatch or inaccessible listed evidence, `2` invalid input or operational error.

Manifest JSON must not contain duplicate object keys (including nested keys) or the non-standard constants `NaN`, `Infinity`, and `-Infinity`. These inputs, and floating-point numbers that overflow to non-finite values (for example `1e999`), are rejected with exit code `2` before evidence hashing. Excessive JSON nesting beyond the decoder limit is also rejected with exit code `2` rather than an unhandled traceback. This validation does not authenticate the manifest.

Manifest input must be a regular UTF-8 file of at most 4 MiB (4,194,304 bytes, including whitespace). The reader requests at most one byte beyond this limit and rejects oversize input before JSON parsing. Detected directories and special files such as FIFOs are rejected before opening. The opened manifest descriptor is also checked for regular-file type before any read or JSON decoding. POSIX manifest opening uses the same read-only nonblocking opener as evidence files, mitigating FIFO substitution between the initial check and open. The existing 4 MiB limit remains unchanged. Manifest loading also compares the initial path stat device/inode with the opened descriptor, compares the descriptor mode, link count, size, mtime and ctime immediately before and after the bounded read, and compares the final path stat device/inode with the descriptor before decoding JSON. Observable identity mismatches, zero inode values or sampled metadata changes are rejected. The sampled size must be within the input limit, and the returned byte count must equal the sampled size. The same bounded control reader applies to signatures and signing keys; incomplete but otherwise parseable input is rejected before parsing or cryptographic use. Stable symlinks and hard links to regular manifests remain permitted; the manifest itself is not subject to the evidence single-link policy. This is a best-effort detector dependent on filesystem metadata, not authentication, continuous monitoring, an atomic snapshot, or protection against every concurrent change. Filesystems with unavailable or inconsistent identity information may be rejected. The CLI `create` command also rejects serialized output that would exceed the limit using conservative CRLF newline accounting; split large file lists into multiple manifests. This bounds the input read, not total memory, runtime, verification-report size or evidence-file size. Use stable local files; concurrent replacement between checks and opening is outside this tool's security model.

Verification validates the structure of every manifest entry (object type, path string, lowercase SHA-256 digest, portable relative path syntax, and exact duplicate path names) before resolving or hashing any listed evidence file. Malformed entries produce exit code `2` without evidence hashing. After structural validation, filesystem errors and mismatches remain per-file results (exit `1`); report order follows manifest order.

Path names use a conservative cross-platform lexical policy: `/` separates nonempty components (at most 128). Dot and parent components, trailing ASCII spaces/dots, Windows-reserved device names (including extensions), Windows-forbidden punctuation, ASCII control characters 0–31 and unpaired surrogate code points are rejected on every OS. Both create and verify validate the complete path list before evidence resolution or hashing. This intentionally rejects some previously accepted POSIX filenames; invalid lexical paths now produce exit code `2` instead of a per-file error in verify. Rename incompatible files before creating a new manifest; do not silently rewrite existing evidence paths. This is not a guarantee of portability: filesystem-specific limits, filesystem aliases (including hard links and short names), and concurrent changes remain outside this lexical check.

Both create and verify also reject conflicting spellings of any listed path component under the same parent when they share a conservative Unicode comparison key (NFC, casefold, NFC). This includes directory prefixes, even when the leaf filenames differ. A listed file cannot also be an ancestor directory of another listed file (for example, `a` and `a/b`); both input orders are rejected. Complete structural preflight precedes evidence-root resolution, including for authenticated manifests. The original spelling is preserved; no path is automatically renamed. This policy can reject distinct files on case-sensitive filesystems and is not an exact model of any particular filesystem's case or normalization rules. It detects collisions among listed paths only, not all aliases or unlisted directory entries. Rejections occur before evidence file resolution or hashing (exit code `2`).

Evidence files must report exactly one hard link (`st_nlink == 1`) at the time of the file check. A file with additional hard links is rejected, including aliases not listed in the manifest and aliases elsewhere on the same filesystem. An unavailable or zero link count is not accepted. This intentionally conservative rule rejects even legitimate multiply linked files: if appropriate, use independent copies in a trusted evidence directory rather than modifying originals. The affected file is not hashed; create exits `2`, while verify records a per-file error (exit `1`). In addition, different listed names with the same sampled device/inode identity are rejected within one operation, even when the reported link count is one. The second alias is not hashed. Identical content in independent files remains supported. The rule depends on trustworthy filesystem metadata and is not a proof of origin, a general alias detector, or protection against concurrent link changes. It does not apply to the manifest file itself.

Evidence hashing supplies at most the initial descriptor size to the SHA-256 function, followed by a one-byte EOF probe. Unexpected EOF, invalid read progress or additional bytes cause failure rather than accepting a partial file or following indefinite growth. This is a bound on bytes delivered to the hashing reader, not a bound on OS buffering, initial file size, elapsed time or total I/O. During evidence hashing, the tool compares metadata from the same open file descriptor immediately before and after reading (mode, link count, size, modification and ctime timestamps). Observable differences cause create to fail or verify to report a per-file error, even when the computed digest matches. This is a best-effort change detector; timestamp semantics and precision vary across systems (including Windows ctime). It does not guarantee a stable snapshot, detect every same-size or reverted modification, or prevent hostile concurrent replacements before opening or after checking. Use stable, trusted evidence.

Before hashing, the tool also compares the final component's checked `lstat()` device/inode identity with the opened descriptor's `fstat()` identity, rejecting a mismatch or a zero inode, and checks that the opened descriptor describes a regular single-link file. This reduces the chance of accepting a different file substituted between validation and opening, including one with identical contents. Filesystems with unavailable or inconsistent identity metadata may be rejected. Identity comparison alone does not prevent opening a substituted object, guarantee that ancestors or the pathname remain unchanged, detect inode reuse, or provide an atomic snapshot or comprehensive TOCTOU protection. Use stable, trusted directories.

After hashing and before closing the descriptor, the tool revalidates the listed path beneath the resolved root and compares the final component's device/inode identity with that of the hashed descriptor. A missing, invalid or observably replaced pathname is rejected, even when the old descriptor remained stable. This is a sampled check, not continuous path monitoring: it does not guarantee ancestor identity, detect a change reverted before revalidation, prevent changes after revalidation, or remove race windows within the checks. Native open-parent rename regression tests target POSIX; a simulated post-read identity mismatch also exercises the check across platforms.

On POSIX, evidence files are opened read-only with `O_NONBLOCK` so a FIFO substituted after path validation does not block waiting for a writer before descriptor checks. The existing descriptor identity and regular-file checks reject the substituted FIFO before hashing. Regular local files retain normal read behavior. This mitigation applies to evidence and manifest opening on POSIX, not Windows special-file behavior, all device types, network filesystem stalls, or all concurrent filesystem races. No general time limit or guarantee of nonblocking I/O is implied.

For both evidence and manifests, the initial pathname metadata and opened descriptor, and the post-read descriptor and final pathname metadata, are additionally compared for size and modification timestamp. This detects observable same-inode changes in the gaps between those samples. Other metadata fields can have different representations across pathname and descriptor stat calls, so only size and mtime are compared across those interfaces. This remains best-effort and does not provide atomicity, a consistent multi-file snapshot, or immunity to reverted modifications and changes after the last sample.

On POSIX, evidence opening additionally walks the validated relative path using directory descriptors (`dir_fd`), `O_DIRECTORY` and `O_NOFOLLOW` for directories, and `O_NOFOLLOW` plus `O_NONBLOCK` for the final file. The resolved root itself is opened without following a final-component symlink. One root descriptor is retained for the entire create or verify operation, with sampled identity checks at opening, before individual entries and at successful completion. Traversal uses duplicates of that descriptor, retains opened descendant directories until leaf opening completes, and compares their actual device/inode identities with pathname samples before returning the leaf. The bounded path-depth policy limits traversal descriptors, but does not ensure a filesystem snapshot. Observable root replacement causes the operation to fail rather than produce a successful result from different roots. The persistent root descriptor is closed on success and exceptions. If the required POSIX primitives are unavailable, evidence opening fails instead of silently falling back. Existing descriptor and pathname checks still apply. This rejects transient symlink substitutions at those components before hashing, but does not protect ancestors above the resolved root, prevent directories from being renamed after their descriptors are opened, prevent mount changes, or guarantee an atomic snapshot. Windows additionally holds a native directory handle to the resolved root for the lifetime of each create or verify operation. CreateFileW requests directory-listing and attribute access, opens the final component without following reparse points, and omits delete sharing. GetFileInformationByHandleEx checks the directory/reparse attributes and compares its volume and 128-bit file identity with newly opened pathname handles at sampling points. Unavailable native identity or failed opens are errors, not a fallback. This is intended to prevent ordinary Windows root rename/delete while the guard is held and detect observable root changes. For each listed file, Windows also opens each descendant directory with the same no-follow and no-delete-sharing flags, checks the handle attributes and identity, and retains those handles through the read. The final component is opened read-only with OPEN_REPARSE_POINT, checked for disk-file type and absence of directory/reparse attributes, and transferred to a binary Python stream via msvcrt.open_osfhandle. The native leaf handle omits delete sharing and permits read/write sharing; existing sampled file checks still apply. Prefix identities are checked before and after opening and after successful processing. This is absolute-path opening with retained directory guards, not NT RootDirectory-relative traversal. It does not protect ancestors above the resolved root, guarantee that reparse attributes cannot change between samples, prevent every filesystem race or provide an atomic multi-file snapshot. Manifest opening is unchanged. Filesystems that cannot supply these native semantics may be rejected. See the Microsoft Win32 documentation for [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) and [GetFileInformationByHandleEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex). Manifest opening retains its previous behavior. Use trusted, stable local directories on all platforms. Root pinning does not ensure a consistent snapshot of all files, prevent transient root changes between samples, or provide a security boundary against concurrent directory moves.

Each descendant directory identity is also sampled before and after hashing and rechecked at batch completion; a replacement ancestor is rejected even when the leaf file identity is unchanged. Unsupported OS families now fail closed rather than using unguarded evidence opening. These are additional sampled checks, not continuous namespace protection.

After the per-file checks, create revalidates every processed pathname and verify revalidates every matching entry while the root guard remains active. Each check compares the original pathname `lstat()` identity, mode, link count, size, modification and ctime timestamps with a new validated pathname sample. A missing, invalid or observably changed earlier file prevents a successful create (exit 2) or changes that verify entry to an error (exit 1), preserving report order and existing mismatches/errors. Root-level failures can abort the operation (exit 2). The final pass stores one metadata sample per successful entry and does not reopen file contents or rehash files. This is sequential best-effort revalidation, not an atomic snapshot: previously checked files can still change after their last sample, changes can be reverted, and timestamp/identity semantics vary by filesystem. For a point-in-time integrity claim, obtain an independently trusted immutable filesystem snapshot or enforce write exclusion for the entire capture/verification operation. The tool does not create or certify such a snapshot.

## Experimental Windows deny-write mode

Opt in to `--windows-deny-write` on create, verify or verify-signed. This mode is not available on POSIX and rejects unsupported use rather than falling back. It holds all listed leaf handles opened with FILE_SHARE_READ only (no write or delete sharing), plus root and descendant directory guards with read-only sharing, before hashing any file and through batch revalidation. Incompatible existing ordinary writer handles prevent acquisition. A conservative limit of 256 aggregate path components bounds retained handles (including repeated prefixes); exceeding it fails before root resolution. If acquisition or any guarded check fails, the entire operation exits 2 with no partial manifest or verification report. Ordinary hash mismatches still exit 1 on verification. The manifest/signature wire format is unchanged; an opt-in verification report adds a protection mode/scope field.

```powershell
python evidence_integrity.py create --windows-deny-write --root evidence a.txt b.txt
python evidence_integrity.py verify --windows-deny-write --root evidence --manifest manifest.json
```

This mode conservatively requires a local NTFS volume GUID on the actual root, descendant and leaf handles, and matching volume scope; unsupported or unavailable queries fail closed. Native 128-bit file identity, type, reparse attributes and ChangeTime are sampled on the retained leaf handle. This does not certify the storage driver or underlying hardware. The common protected interval begins after all leaf handles are acquired and ends before the first is released, not when the CLI returns or writes stdout. This mode addresses ordinary conflicting write/delete opens of the listed leaf objects; it is not an atomic snapshot, does not prove all namespaces are immutable, and is not a guarantee against privileged writers, filesystem drivers, raw-volume access, metadata-only opens, reparse/mount changes, root ancestor substitution, or unverified filesystem sharing behavior. Directory guards exclude ordinary incompatible write/delete opens. In guarded mode descendant opens use one-component NT RootDirectory-relative NtCreateFile with FILE_OPEN_REPARSE_POINT, followed by native type, identity and reparse checks; relative edges are checked while held. No absolute descendant-open fallback. Guarded root acquisition starts at a local drive-letter volume root and opens each ancestor and the evidence root relative to held native handles, rejecting reparse points and cross-volume roots. Ancestor handles omit delete sharing but allow ordinary writes; the evidence root denies write/delete sharing. Drive-anchor acquisition and supplemental pathname samples remain absolute. Metadata-only operations and privileged namespace changes remain outside the assurance. Control files still use retained-byte validation, not cohort locks. A writable alias or mapping outside validated assumptions, or changes before acquisition/after release, remain outside the assurance. External trusted isolation remains necessary for point-in-time forensic claims. Explicit `--assume-stable-tree` retains the earlier sampled behavior; there is no implicit CLI default. This experimental mode is not release approval. See the [TOCTOU hardening design and acceptance matrix](docs/toctou-hardening-design.md).

## Experimental Linux Btrfs snapshot mode

On Linux x86-64, an operator may supply a trusted, externally provisioned, root-owned read-only Btrfs snapshot root and its independently obtained canonical UUID. Use `--linux-btrfs-snapshot UUID` with create, verify or verify-signed. The CLI must run unprivileged. It checks the native subvolume read-only flag (not merely a read-only mount), snapshot and parent UUID, generation, device and descriptor mount identity. It uses openat2 with no symlink, magic-link or mount crossings; validates a held O_PATH regular single-link object before opening it via trusted procfs; checks actual file subvolume identity and root scope before/during/after the batch. No automatic provisioning or weaker fallback. The manifest/signature wire formats are unchanged.

The operator must trust snapshot provenance, root-owned provisioning, kernel, procfs, storage and mount namespace. Privileged actors, idmapped mounts and namespace manipulation outside that trust boundary are not covered. A UUID is an identifier, not a cryptographic attestation. Only Linux x86-64 is targeted by this provider. Native synthetic fixture validation is required before relying on this mode.

## Experimental macOS APFS snapshot mode

On macOS arm64, use `--macos-apfs-snapshot SOURCE` with create, verify or verify-signed, where SOURCE is an independently obtained exact native mount-source identifier (for example `snapshot-name@/dev/diskXsY`, using the actual device identifier). Run without root privileges; supply the root of a trusted administrator-mounted local APFS snapshot. The native fstatfs flags must include MNT_SNAPSHOT, MNT_RDONLY, MNT_LOCAL and MNT_NODEV; mount owner must be root. The held root, each opened directory and each leaf must match the descriptor filesystem/mount scope. The tool does not create snapshots or mount volumes; generic read-only APFS volumes are rejected. No fallback.

The source is a host-local identifier, not a persistent UUID or cryptographic attestation; trust the operator's independent snapshot provenance, mount namespace, kernel and storage. As in Btrfs mode the manifest/signature formats are unchanged. Both snapshot modes require native positive/negative fixture verification. No support is claimed for other filesystem providers.

## Experimental signed manifests

The development candidate includes detached Ed25519 signing and explicit signed verification. These commands have native CI evidence, including hash-enforced wheel installation and POSIX and Windows terminal tests at 2cd3fb3; the follow-up candidate requires its own regression and independent security review. Do not use this candidate for production evidence. The cumulative release candidate is subject to the explicit [release gate and review record](docs/release-gate.md). A separate release-provider CI check intentionally fails for the current unapproved OpenSSL provider; functional test success does not override it.

Install optional signing dependencies in a trusted environment from the reviewed dependency set. The candidate requirements-signing.txt pins exact versions and ten wheel hashes for the tested matrix. In a fresh virtual environment, use `python -m pip install --require-hashes --only-binary=:all: -r requirements-signing.txt`. Other architectures/wheel variants may be rejected. See [design](docs/security-and-signature-design.md) and [dependency notes](docs/signing-dependency-candidate.md).

Use an independently obtained Ed25519 SPKI public key and an encrypted PKCS#8 private key. Keep keys, manifest and signature outside the evidence root in trusted storage. Signing requires an interactive terminal for the non-echoing passphrase; passwords are not accepted as CLI arguments or environment variables. On some Windows consoles Ctrl+V can be delivered to Python getpass as U+0016 rather than pasted text. If the interactive passphrase contains that character, signing rejects it without attempting key decryption or modifying the input. Type the passphrase manually or use a terminal paste command that inserts text; paste support varies by host. Interactive passphrases containing literal U+0016 are unsupported on all platforms. The internal bytes-based key API is unchanged. Never put real passphrases in command history or diagnostics.

```sh
python evidence_integrity.py sign --manifest manifest.json --private-key signer.pem > manifest.sig
python evidence_integrity.py verify-signed --assume-stable-tree --root ./evidence --manifest manifest.json --signature manifest.sig --public-key trusted.pem
```

The signature is 128 lowercase ASCII hex characters plus a newline. Use redirection that preserves ASCII/UTF-8 bytes (for example a POSIX shell or cmd.exe); legacy Windows PowerShell redirection can write UTF-16 and is not suitable. Never redirect output to an input file: the shell may truncate it before Python starts. The sign command attests to validated manifest bytes, not to the evidence contents at signing time. Verify the collection and trust its capture procedure before signing.

Signed verification authenticates the exact retained manifest bytes before JSON parsing or evidence I/O. It rejects unknown manifest fields, missing/invalid signatures and wrong keys; no fallback to unsigned verification. Exit 0 means signature valid and all listed evidence matched; exit 1 means authenticated manifest but at least one evidence mismatch/error; exit 2 means invalid input, authentication failure or operation error. The authentication object reports the fixed protocol, verified=true and SHA-256 fingerprint of the raw public key. This fingerprint identifies the supplied key; trust must come from outside the tool. Unsigned verify remains available and never authenticates a manifest. Callers requiring authenticity must explicitly require verify-signed.

The protocol does not certify authorship, freshness, chain of custody, completeness, or point-in-time snapshot consistency. A valid signature proves only that the supplied key verifies the supplied manifest bytes.

## Security model and limits

Unsigned verification checks content against a supplied manifest without authenticating it. Signed verification authenticates manifest bytes relative to an explicitly trusted key. Neither mode proves authorship, establishes chain of custody, or proves that the directory contains no additional files. It checks explicit relative paths and rejects traversal and symbolic links, junctions and other reparse points when exposed by `lstat()` on each listed path component below the resolved evidence root. Junction detection does not require `Path.is_junction()` (introduced in Python 3.12). Some Windows reparse types may be resolved by the operating system rather than exposed by `lstat()`; this is not a guarantee that all reparse points are detected. The explicitly supplied root is resolved before checking its descendants. It is not a sandbox and is not designed to withstand concurrent hostile filesystem changes. Use a trusted, stable local directory and keep manifests separate from untrusted evidence. Manifest paths may themselves be sensitive; inspect before sharing. Never publish actual client evidence or private manifests.
