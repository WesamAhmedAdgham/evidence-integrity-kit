## C. Threat model

The tool compares explicitly listed regular file bytes against SHA-256 digests. Signed verification also authenticates the exact retained manifest bytes against an independently selected Ed25519 trust anchor before parsing or evidence access. The reported fingerprint is SHA-256 of the raw 32-byte public key. The detached protocol includes a domain string and version. Signature text accepts lowercase hexadecimal and the specified optional line endings.

An untrusted party may supply manifest bytes, invalid signatures, path entries or files in a handed-off collection. The bounded parser and path preflight apply before evidence access, and protected modes reject unavailable queries. Signing takes an encrypted PKCS#8 key in the supported profile from trusted storage and a passphrase from a trusted terminal. General DER, other KDFs and arbitrary key provisioning are outside the supported format. The public Python API retains sampled behavior by default and the CLI requires explicit selection.

Trusted components include the interpreter, OS, filesystem and storage drivers, cryptographic providers, install chain, operator identity, key channel and control storage. For point-in-time evidence, acquire an immutable snapshot or maintain effective writer and namespace exclusion for the full capture and comparison interval. Validate this on the deployment storage and retain the artifacts in trusted custody. A caller's assertion in sampled mode is reported as an assertion. Windows guarded mode covers ordinary share conflicts inside the common handle lifetime. Linux Btrfs mode covers a provisioned read-only subvolume in a trusted namespace and checks the supplied identity. APFS native acceptance belongs to its deferred PR.

Residual risks include privileged and raw-storage writes, compromised drivers or interpreter, current-directory or namespace manipulation outside the declared boundary, missed transient samples, writable aliases outside the assumed environment, time-consuming evidence I/O, terminal memory retention, key compromise and replay. External procedures establish snapshot provenance, capture time, scope, completeness and legal custody when required. The format carries no trusted timestamps, capture-mode assertion, revocation or identity certificates.

References: [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032) · [RFC 8410](https://www.rfc-editor.org/rfc/rfc8410) · [RFC 8018](https://www.rfc-editor.org/rfc/rfc8018) · [Windows CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) · [Linux openat2](https://man7.org/linux/man-pages/man2/openat2.2.html) · [Btrfs subvolumes](https://btrfs.readthedocs.io/en/latest/btrfs-subvolume.html)

## G. Owner decision packet

1. **CFFI provenance.** Recommended: permit a documented official-wheel evidence route after independent review of exact hashes, distribution ownership, native inputs and applicable advisories. Alternative: maintain qualified source-built or separately trusted native distributions. The first lowers ongoing build cost and retains publisher/build-opacity risk. The second moves that risk to tooling and release maintenance. The existing CFFI gate remains in force until the decision and evidence are recorded.
2. **Filesystem assurance.** Recommended: approve point-in-time operation only for specifically validated immutable or isolated environments. Alternative: restrict signed release scope further to a validated native or operational profile. This trades platform availability for a narrower operational trust boundary. Guarded Windows and sampled modes alone support narrower claims. Merging the signed candidate remains blocked pending acceptance and evidence.
3. **Key policy.** Recommended: enforce stronger provisioning operationally for new keys and allow legacy import only under documented controlled use. Alternative: raise the runtime minimum after impact review and migration guidance. Stronger runtime admission reduces exposure from weak encryption with a compatibility cost. Neither decision replaces high-entropy passphrases or trusted private-key storage.
4. **Human review enforcement.** Recommended: configure the active main ruleset to require independent approval of the latest revision, with a named reviewer available. Alternative: constrain release authority and track an exact-head approval record as a manual gate. Automated enforcement lowers process-bypass risk and requires an available separate reviewer. The existing twelve CI contexts stay required.
